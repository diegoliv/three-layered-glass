# Implementation analysis: 0.2.0 vs 0.3.0

This document compares the original 0.2 package implementation with the final panel-demo renderer incorporated into 0.3.

## 0.2 render model

The 0.2 `LayeredGlassComposer` used one render sequence per glass mesh:

1. Hide all layered glass meshes and render the opaque scene to `LayeredGlass.Base`.
2. Sort glass meshes back-to-front using material priority and distance from the mesh origin to the camera.
3. Render the selected mesh's back-face world positions to an `RGBA16F` target.
4. Render the selected mesh's back-face world normals to another `RGBA16F` target.
5. Copy the accumulated color into the next ping-pong render target.
6. Render the mesh's front faces with `LayeredGlassMaterial`.
7. Swap the read/write targets and repeat for the next mesh.

This architecture supported arbitrary closed meshes and measured a real screen-space exit surface. Its main constraint was that the entire mesh received one position in a global object order.

## Why the 0.2 order failed

Sorting by camera distance cannot describe cases where different pixels see a different nearest object. Even replacing radial distance with camera-space depth only changes the moment at which two objects swap. It does not remove the global swap.

The opaque scene was also flattened before the glass loop. A refracted ray could sample an opaque image, but opaque meshes did not participate as world-space intersections after the ray changed direction.

## 0.2 optical model

The 0.2 fragment shader evaluated one glass mesh at a time:

- Air-to-glass refraction at the front face.
- Iterative tangent-plane search against the back-position/back-normal textures.
- Glass-to-air refraction at the estimated exit.
- Schlick Fresnel at both interfaces.
- Beer-Lambert attenuation using measured optical distance.
- A nine-tap texture blur for rough transmission.
- RGB dispersion offsets around one final refracted UV.
- Procedural environment reflection.

Roughness and dispersion mainly affected the final flattened source sample. They did not launch independent paths through every subsequent glass layer.

## 0.3 render model

The 0.3 `LayeredGlassComposer` renders the normal Three.js scene once, excluding layered glass meshes. It then runs one fullscreen resolver.

Every fragment:

1. Reconstructs the world-space camera ray.
2. Intersects the ray against all registered analytic volumes.
3. Selects the nearest hit for that pixel.
4. If the hit is glass, refracts through the entry and exit interfaces and continues from the new world-space position.
5. If the hit is an opaque blocker, terminates at that exact hit point.
6. Repeats until no volume remains or `maxTraversals` is reached.

No glass mesh is assigned a global draw-order position. Glass and registered opaque blockers use the same nearest-hit operation.

## 0.3 optical model

Optical properties are packed per volume rather than shared globally.

- `uVolumeOpticalA`: IOR, roughness, attenuation distance, reflection strength.
- `uVolumeOpticalB`: attenuation color and dispersion.
- `uVolumeMeta`: kind, shape, refraction reach, body-tint strength.
- `uVolumeBounds`: local half extents and rounded radius.

Dispersion is evaluated as three complete paths. Red, green, and blue use slightly different IOR values at every glass interface. Roughness perturbs the entry and exit normals at every interface, then contributes to terminal blur.

Fresnel reflection, absorption, body tint, rough scattering, and optical distance accumulate as the ray crosses the volume list.

## Opaque integration

Opaque meshes remain normal Three.js meshes. Registering one as a blocker adds an analytic proxy without replacing its material.

- If an opaque blocker is the first hit, the resolver preserves the normal base render.
- If a refracted ray reaches the blocker, the optical path terminates at its world-space intersection.
- Other unregistered opaque geometry remains available through base color and depth screen-space fallback.

This preserves ordinary opaque-to-opaque depth behavior while fixing registered opaque-to-glass ordering.

## Mobile compatibility

The 0.2 implementation required floating-point color attachments because world positions and normals were rendered into `RGBA16F` buffers.

The 0.3 analytic resolver does not need back-face data targets. It uses float color targets when available for HDR range, but can fall back to unsigned-byte color targets. WebGL2 remains required.

## Performance tradeoff

0.2 cost scaled primarily with draw passes per glass object:

```text
base render + N × (2 back-face passes + front-face pass + fullscreen copy)
```

0.3 cost scales primarily with fragment work:

```text
base render + fullscreen pixels × volumes tested × spectral/rough paths
```

The 0.3 model removes repeated geometry passes and ordering artifacts, but large screen coverage and high volume counts can be expensive. `maxVolumes`, `maxTraversals`, pixel ratio, and rough/spectral activation are the main quality controls.

## Capability tradeoff

0.2 remains better for arbitrary closed meshes whose silhouettes cannot be represented analytically.

0.3 is better for supported analytic volumes where stable multi-layer ordering is required. The package supports box, rounded-box, sphere, and transformed sphere volumes. A future BVH backend can replace analytic intersections while preserving the 0.3 traversal and material accumulation model.
